# MyLab：研究生实验室管理平台

MyLab 是一个由学习者手写 Go 后端、逐章实现并验收的 Web 项目。后端使用 go-zero，以 API 服务和 RPC 服务逐步建立微服务结构；业务数据直接持久化到 MySQL。前端由助手实现并与实际接口联调。

当前先完成独立的实验室管理平台，Agent 接入留待后续讨论。

## 仓库结构

```text
mylab-course/      日常带练和手写代码的位置
mylab-final/       预留的完整可运行版本发布目录，目前只有说明
docs/chapters/     随开发增加的章节说明、验证方法和面试讨论
```

教学版和最终版在同一个 Git 仓库中维护，不在子目录中执行 git init。教学版使用自己的 go.mod；最终版发布时再建立独立的 go.mod 和启动说明。

## 已确定的第一版业务边界

- 一个实验室，一位老师。
- 用户以自定义用户名和密码登录。
- 老师创建学生账号，并指定、撤销学生管理员。
- 学生管理员可以创建、停用普通学生账号。
- 第一个业务闭环是账号和权限管理，组会、提问、资源等功能随需求逐个讨论。

## 带练规则

- 学习者创建、修改后端实现；助手负责解释、审阅、验证和排错。需要助手代写时由学习者明确提出。
- 每轮只实现一个连贯、可验证的小单元，先说明它在请求链中的位置。
- 每章解释与实际代码有关的面试追问，不把尚未实现的能力当作项目成果。
- 存储直接使用 MySQL；当前健康检查没有业务数据，不引入内存用户仓库。
- 新章节在现有代码验证完成、学习者提交上一章之后开始；章节总数随需求确定。
- 完整版从经过验证的教学代码整理而来，不提前维护两套业务实现。

## 章节与 Git 标签

| 章节 | 目标 | 起点 | 终点 |
| --- | --- | --- | --- |
| [01](docs/chapters/01.md) | 启动 go-zero API，完成健康检查并读懂请求链 | 原始 Chi HTTP 入口，尚无教学目录 | `/healthz` 返回 `{"status":"ok"}`，实现已验收，待提交 `01-end` |
| [02](docs/chapters/02.md) | 建立用户 RPC 服务，直接接入 MySQL | 第一章完成状态 | 待逐步实现与验收 |

`01-start`、`01-end` 是由学习者在对应提交上创建的标签。后续章节同理；标签一旦创建，不随开发移动。目前 `01-start` 实际指向原始提交 `b8d94a8`，包含根目录的 Chi HTTP 入口：监听 `8080`，`/healthz` 返回纯文本 `ok`，尚无教学目录。本章将代码整理为教学目录中的 go-zero 服务。后续章节起点应保留上一章可运行的能力。

复习某个版本时，在工作区修改已经提交或妥善保存后执行：

```bash
git switch --detach 01-start
```

标签对应整个仓库的快照，查看早期标签时，目录内容也回到当时状态。需要从旧版本重新练习时，可以创建练习分支：

```bash
git switch -c codex/review-01 01-start
```

日常学习保留在当前开发分支。章节提交、标签创建和远端推送由学习者执行。
